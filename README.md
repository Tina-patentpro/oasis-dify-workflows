# oasis-dify-workflows · 专利撰写 Dify 工作流设计源

> **请先读这一段，避免误解资产身份。**
> 本仓库公开的是 **12 份本地维护的 Dify 工作流设计源 YML**（`kind: app` 的 DSL 草稿），
> **不是 Dify 实例上已发布应用的导出包**，也**没有**在任何新环境中完成导入或运行验证。
> 源项目中央登记册把 14 个流程的 `current_candidate_yml` 全部登记为 `undesignated`、
> `contract_state` 为 `gap_confirmed`、`evidence_status` 为 `STATIC_ONLY`；
> 登记册明文写着："它不证明任何 YML 已经成功导入、运行或发布。"
>
> 本次发布只是把**有明确选取依据的具名历史版本快照**整理成可下载、可解析、可审阅的资源，
> **没有**把它们升格为"当前候选"，**没有**宣称导入成功、运行成功或专业接受。
> 详见 [验证范围与限制](docs/verification-and-limits.md)。

配套 Skills 见姊妹仓库 `oasis-patent-skills`。

## 1. 这个项目解决什么问题，面向谁

中国专利撰写的 14 个业务节点（技术背景研究 → TRIZ → 检索 → 方案筛选 → 交底 → 权项 →
说明书 → 复检 → 撰写计划 → 发明人确认 → 正式稿 → 终检 → OA 答复）如果每次都靠口头约定，
很难复用。把这些节点编排成 Dify 工作流，可以把模型、提示词、变量、Schema、Code 节点和检查位置
固化下来。

但**工作流设计稿**和**线上可运行的应用**是两回事。本仓库解决的是前者的公开问题：

- 让开发者／研究者能看到真实的中文专利业务 Dify DSL 长什么样，节点怎么排、提示词怎么写、
  变量与 Schema 怎么定义；
- 让想自建类似能力的人有一份可参考、可 diff、可讨论的起点；
- 明确保留"设计源 / 实例导入 / 运行 / 专业接受"之间的证据边界，不把源码存在当成服务可用。

**面向谁：** Dify 自托管开发者、专利业务 Agent 的研究与教学者、想评估这套编排思路的工程团队。
**不面向：** 想直接 `docker compose up` 就得到一套可收费运行的专利撰写服务的人——本仓库不提供
模型凭据、插件包、环境变量真实值、后台服务或部署脚本。

## 4. 下载、导入与配置

完整步骤见 [导入与配置指南](docs/import-guide.md)。要点：

```bash
git clone https://github.com/Tina-patentpro/oasis-dify-workflows.git
cd oasis-dify-workflows
```

1. **先做只读审阅**：YML 是设计源，建议先在文本编辑器或 YAML 查看器里看节点、提示词和变量，
   不要一上来就往生产实例导入。
2. **准备你自己的 Dify 环境**：需要一个你能完全控制的 Dify 实例。本仓库**不含**服务端地址、
   API Key、环境变量真实值或凭据。
3. **导入**：用 Dify 的「导入 DSL / 创建应用」功能导入单个 `.yml`。不同 Dify 版本对
   `version: 0.1.x ~ 0.6.0` 的 DSL schema 兼容性不同，**本仓库未验证任何具体版本的导入结果**。
4. **配置依赖**：按 [依赖说明](docs/dependencies.md) 补齐模型供应商、插件、工具与环境变量。
   其中 `Flow-1-1` 的 HTTP 请求头含占位值 `YOUR_API_KEY_HERE`，**必须替换为你自己的凭据**；
   `Flow-2-6` 有 6 处 `{{#…server_…#}}` 形式的 Dify 工具凭据模板引用，导入后需重新绑定。
5. **隔离验证**：建议先建一个独立的临时应用验证，**不要覆盖已有应用、草稿、环境变量或发布状态**。

**不要做的事**：不要把生产服务器地址写成公共免费接口；不要把这些 YML 当成"一键可用的服务"；
不要在未核对插件来源的情况下启用第三方插件。

## 5. 需要哪些模型、工具、插件与服务，哪些可能产生费用

完整逐项清单见 [依赖说明](docs/dependencies.md)。总体情况（从 YML 机械提取）：

| 依赖类型 | 实际情况 |
|---|---|
| 模型供应商 | 多数流程引用 `langgenius/openrouter/openrouter`；`Flow-3-10` 引用 `anthropic`；`Flow-1-4` 未检出模型 provider |
| 环境变量 | `Flow-1-3` 声明 `SERPER_API_KEY`（描述中说明"请在 Dify 平台环境变量中配置"）；YML 内**无真实值** |
| 工具凭据模板 | `Flow-2-6` 有 6 处 `{{#<id>.server_*#}}` 模板引用，是 Dify 工具凭据的变量占位，需导入后自行绑定 |
| HTTP 请求头 | `Flow-1-1` 含已被脱敏的 `Bearer YOUR_API_KEY_HERE`，需自行配置 |
| 知识库 / 文件服务 / 插件包 | 本仓库**不分发**，YML 中若引用需你自行准备 |

**费用**：下载本仓库免费。但模型推理（OpenRouter、Anthropic 等）、检索服务（如 Serper）、
图像服务通常按量计费，**费用由你与服务商结算**。本仓库不提供免费推理接口、不承诺任何额度，
也不含任何可用于直接调用的真实凭据。

## 6. 输入什么、输出什么，缺件时如何处理

这些 YML 是**工作流编排**，不是函数库：输入输出由 Dify 应用的 `start` 节点变量与各节点的
Schema 决定，导入后由你在实例中配置。逐流程的输入输出约定、依赖与已知问题见各目录下的
`NOTES.md`。

- **设计目标**：按 14 节点业务合同（`14节点清单V3.4.0`）组织，覆盖从技术背景研究到审查意见答复；
- **实际状态**：源登记册明确 `contract_state=gap_confirmed`，即**现有资产尚未达到 V3.4.0 目标合同**；
  请把 YML 当作"历史实现基线"而不是"已完成合同"；
- **缺件处理**：导入后如缺少模型、插件、环境变量或知识库引用，Dify 会报配置缺失。请按
  `NOTES.md` 与 [依赖说明](docs/dependencies.md) 逐项补齐或明确停用对应分支，**不要**用删除
  必需节点的方式让图"看起来能导入"；
- **示例**：本仓库不提供实测运行样例，也不把模型生成文稿写成"成功案例"。
